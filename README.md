# ORBIT

Operational Reasoning Bot for Intelligent Tasks. Always live: merging to main deploys, and `GET /status` says what is real.

Every capability is a port that reports `live`, `mock`, `degraded` or `down`. Every answer carries its provenance, so mock data can't pass as real. `policy` fails closed.

```bash
pnpm install && pnpm test && pnpm start
curl localhost:8790/status
```

Open `/` for web chat. Every reply is tagged `live` or `mock`, and the model is told which parts of ORBIT are not connected.

## Chat tools

For the owner, the model can call ORBIT's own actions during a reply (up to 20 tool rounds; a reply ends as soon as it has its answer, and an identical call that keeps failing the same way is stopped early, see `docs/assistant.md`): `memory_search`, `memory_read`, `github_repo_status`, `jobs_list` (a compact row per job and the true total), `job_status` (last 20 events and how many were left out), `job_steer`, `notify` and `job_launch`, plus the `ops_*` server tools when the helper is installed. Each call is checked by `decide("agent", tool)`, and the reply lists every call with its provenance. Structured tool calls from the provider run, and so does one narrow exception: a complete, well-formed DeepSeek DSML block written as text on a step offered tools, naming only those tools, is recovered and run through the same checks, with a note on the reply. Any other response that writes a tool call as text is never run or shown as the answer; ORBIT asks the model once more and otherwise ends the reply with an error (`docs/tool-protocol-leaks.md`). Each call has a deadline (180 s by default). A call that runs past it ends the turn and frees the thread. If the call may have had an effect, it is shown as outcome unknown and is never retried automatically (`docs/tool-deadlines.md`). `job_launch` only creates a proposal; the page shows it with Confirm and Cancel, and only a click calls the launcher (`POST /chat/proposals/:id/confirm`). Anyone else, or a model that cannot call tools (the mock), gets none and is told so. The owner also gets seven read-only pull-request inspection tools (`pr_inspect`, `pr_files`, `pr_diff`, `pr_checks`, `pr_check_log`, `pr_discussion`, `pr_text`): head and base SHAs, a paged diff, every check with a failure excerpt, and every review and comment in full, all pinned to the head they were read at and marked stale if it moves. A first call needs no SHA or digest (optional arguments are null or left out); a long text is read chunk by chunk with the exact `continuation.next` arguments each chunk returns, pinned to its head and digest, until `next` is null, and a changed head or text returns a `restart` instead of mixing versions. They only read and never decide readiness. `Verdict:` text in comments is untrusted; a conversation comment shows `orbitReview: verified` (with the job's recorded verdict, job id and reviewed commit) only when ORBIT's own job record, comment id, exact posted text and posting account all match. See `docs/pr-inspection.md`.

**Session discovery (Assistant only).** In the Assistant, the owner's model also gets two read-only tools, `sessions_list` and `session_inspect`, to find the other conversations (the Assistant itself and each chat thread) by id, kind, title, open/archived, whether a reply is running and the last message time, and the jobs a thread launched or steered (from its confirmed cards) with each job's own state. They never return a transcript or a summary, page with a cursor (at most 25 per page), treat every title and excerpt as untrusted data, and are refused in Chat. Contracts, adapters, limits and follow-ups: `docs/adr/0001-session-registry.md`. **Work sessions (slice 4):** confirming a launch records a durable work session (`work:<uuid>`, stored in `<state>/work-sessions.json`) that names the conversation the launch was proposed in (taken from the server's turn context, never from model text) and links its runs; the job carries the same link from the moment it is registered, so a restart reconciles an interrupted launch from the job record instead of guessing, and never relaunches it. Separate launches are separate work sessions unless the owner's confirmation explicitly attaches a follow-up or retry from the same conversation. Schema, trust boundary, failure handling and acceptance: `docs/adr/0002-work-sessions.md`.

## Threads

Conversations other than the Assistant are **sessions**, on the **Sessions** page (`/sessions`, one session at `/sessions/<id>`; formerly Chat, and old `/#chat` links and `/chat` paths still lead to the same session). They are stored on the server as threads, shared by every device, owner only, kept until archived (nothing is deleted). The header shows the open session's title; its picker lists, opens, creates, renames and archives sessions, restores the selection after a refresh, and shows proposal cards with their final state and the job or operation id. The model's context is built from the stored thread, including earlier tool calls and results, with per-thread compaction and a rolling recent-work note. Storage, routes, concurrency, migration, budgets, the recent-context interface and the proposal lifecycle are in `docs/threads.md`.

The page opens on the **Assistant** (`/`, `/#assistant`): one server-owned rolling conversation, the same on every device, stored as small per-turn chunk files in `<state>/assistant/` with an active window and a kept archive, and sent to the model under a hard character budget plus a cumulative rolling summary of the archived turns (`docs/rolling-summaries.md`). Chat stays at `/#chat`; each thread has its own address, `/#chat/<thread id>`, so tabs can show different threads (`docs/threads.md`, "Addresses"). On a phone the page is an app shell (fixed header and composer, only the conversation scrolls, sized to the visible area including the iOS keyboard) with a small set of design tokens: `docs/web-shell.md`. Layout, budgets, archive policy, concurrency and crash behaviour: `docs/assistant.md`; diagrams of the page/server sequence (including restarts) and the rolling memory: `docs/assistant-architecture.md`.

**Photos.** In the Assistant and in a session, the owner can attach 1–10 photos to a message (library or camera, optional caption). The browser shrinks each to at most 1600 px and about 500 KB and re-encodes it, so EXIF and GPS are dropped and no original is uploaded. The server checks every byte again, accepts only a normalized baseline JPEG, and stores it privately in `<state>/attachments/`, scoped to its conversation. A vision-capable primary model receives the stored copies as real image input. A model that cannot take photos, including the paid OpenRouter fallback, refuses the turn with the reason. **Earlier photos:** the owner's model can find sent photos by conversation and day (`photos_list`, metadata only, in Rai's time zone) and look at selected ones again (`photos_inspect`, real image input in the next model request of that reply, within the same 10-photo/10 MiB bound), so "Can you see the images I uploaded today?" works from another conversation without re-uploading. The Assistant reaches every conversation, a chat thread only its own; every ref is re-authorized on each use. **Recall:** `photos_list` also finds photos by words in their caption or conversation title (a metadata text match, never a search of image content), and `photos_show` displays stored photos as a gallery under the reply, kept with the conversation, without sending any image to the model ("Show the second one again" reuses the gallery's ordered refs): `docs/photo-recall.md`. Limits, security, provider support and the manual iPhone checklist: `docs/photos.md`. **Description search (opt-in, off by default):** with `ORBIT_PHOTO_SEMANTIC=on` and the dedicated `orbit.openai-embeddings` API-key credential, `photos_search` ranks photos by saved observations, corrections, captions, titles and Rai's follow-ups (keyword + OpenAI embeddings, filesystem cache, hard daily budgets, keyword fallback); it never looks at the photos: `docs/photo-semantic-search.md`. **Photo gallery:** the sidebar's Images section is paged and opens a gallery page (`/#gallery`) in the centre: photos grouped by day or month with an "AI" badge where an observation is saved, an enlarged view with the photo's source, caption, saved observations (limitations, scope, time, context) and Rai's corrections, and a search over the same stored text as `photos_search` that says which words matched where. Read-only: `docs/photo-gallery.md`.

## Server operations (`orbit-ops`)

Seven read-only chat tools (`ops_orbit_status`, `ops_orbit_logs`, `ops_deploy_state`, `ops_host_health`, `ops_tailscale_status`, `ops_vault_sync`, `ops_credentials`) ask a small root helper behind `/run/orbit-ops.sock` (group `orbit-ops`, mode 0660). Fixed named actions only, bounded and redacted, credentials by name/size/date only, no per-read confirmation. It is installed by `deploy/install.sh`, not by a normal deploy: see `docs/orbit-ops.md` for the exact commands, protections and verification.

## Jobs page and pull requests

The owner's page has a Jobs tab next to chat (hidden for anyone else). The list searches, filters (state, health, lane, kind, routine, needs attention) and pages every stored job with a cursor; each row has a descriptive title with the id, lane and routine, state and health kept apart (`not-started`, `quiet` and `launch-failed` stand out), the latest line, times and the PR link. A job opens at `/#jobs/<id>` in five sections: Overview; Links & artifacts (Claude session, orbit-work branch and brief commit, tool commits, project repo and branch, PR, review comments and related jobs, each marked recorded, derived or unavailable); Inputs sent to Claude (the brief and the Routine fire text from a redacted dispatch snapshot ORBIT now records at launch, launch stages from evidence, and every steer as proposed, queued, received or answered); Activity (all retained events, paged); Results & review. The steer box uses `POST /jobs/<id>/steer` because Rai is acting directly. Open chat proposals (launch and steer) are listed from `GET /chat/proposals` with Confirm and Cancel, so they survive the chat reply scrolling away. The page refreshes every 15 seconds while visible without resetting open sections, expanded text, drafts or scroll. Routes, redaction, legacy gaps: `docs/jobs-page.md`.

When a job's summary arrives with status `done` (API or git) and its routine has a project repo in `ORBIT_ROUTINE_REPOS` (`orbit=DragonflyAI-sh/orbit,money-noodle=owner/name`), ORBIT opens a pull request from `orbit/<job-id>` to `main` there, if that branch exists. The token is the systemd credential `orbit.github-orbit-prs` (Pull requests read and write, Contents read). The title and body come from the summary's `## PR title` and `## PR body` sections (the body runs to the end, or to a later `## PR title`); otherwise a title made from the summary's first line (or, failing that, `<routine>: changes from job <id>`, never `ORBIT job <id>`) and the whole summary; which source was used is recorded on the job (`pr.titleSource`), shown on the Jobs page and added to the `PR ready` message. A footer links the session. Nothing is clipped: the summary is stored whole on the job (up to 200,000 characters), and a description over 60,000 characters is split into ordered parts (part 1 is the PR description, the rest are comments marked `<!-- orbit-part … -->`, each under GitHub's 65,536-character limit, and the parts joined are exactly the text). A part that fails to post is recorded (`pr.posted` of `pr.total`), never reported as delivered, and retried every 2 minutes up to 5 times; a part already on the PR is found by its marker and not posted twice. A summary that reached ORBIT only in part over the API (more than 200,000 bytes) is completed from git before anything is opened; one over 200,000 characters is reported and no PR is opened from it. The PR URL is recorded on the job and shown on the page, only one is ever opened, and Rai is told `PR ready: <url>`. A failure to open the PR is recorded, notified and not retried. No branch in the project repo means no PR and no message. Merging stays Rai's.

### Reviews

Jobs have a `kind`: `work` (default) or `review`. When ORBIT *opens* a PR for a work job (not when the PR already existed), it launches one review job on the same Routine with a brief it writes: the PR, the branch `orbit/<work-job>`, read the diff against `main`, run typecheck and tests, look for bugs, security problems and unsupported claims in the PR body, push nothing, and end the summary with `## Findings` and `Verdict: no blocking issues` or `Verdict: blocking issues`. ORBIT starts it itself, so it needs no confirmation click. A review job never opens a PR and never starts a review; there is at most one per work job. When its `done` summary arrives, ORBIT posts it as a comment on the PR (issue-comments API, same `orbit.github-orbit-prs` credential) with a footer naming the ORBIT-recorded verdict, the review job and its session, records the comment URL on both jobs, and tells Rai once: `PR <url>: review done, <verdict>`. The review is posted whole: findings over 60,000 characters go in ordered comments, every part naming the verdict, with the same resume-and-no-duplicate rules as PR descriptions. The verdict is a structured field (`review.verdict`, with `verdictReason`): `blocking issues`, `no blocking issues`, `no verdict` (no `Verdict:` line) or `ambiguous` (conflicting lines, an unknown value, or `no blocking issues` while a finding is marked `[blocking]`, `**blocker**`, `Severity: blocking` or `Blocking:`). Neither of the last two is approval, and the Jobs tab shows them as problems. The full review text stays on the job as evidence (Jobs tab, Open). A launch failure, or a review that ends `failed` or `blocked`, is recorded and notified (a launch failure or a review that ends `failed` or `blocked` is not retried; a failed comment post is). A stalled review is covered by the job alerts. The Jobs tab shows each job's kind, and a work job's review verdict and comment link. The posting credential needs Issues or Pull requests write on the project repo.

**Auto-fix proposals.** After a work job's review settles, ORBIT reads its PR's checks and mergeable state every few minutes (for 48 hours). A failed check or a merge conflict becomes a fix-job **proposal** on the Jobs page, with the failing checks, test names and a redacted log excerpt, the files changed on both sides of a conflict, and the review's findings in its brief; Rai confirms it like any launch. One proposal per PR; a fix job's own PR is watched the same way, and once a chain reaches `ORBIT_AUTO_FIX_MAX_RETRIES` (default 3) Rai gets an urgent notification instead. `ORBIT_AUTO_FIX_ENABLED=false` turns it off. See `docs/auto-fix.md`.

## Memory

Keyword search over the vault, owner only: ORBIT asks tailscaled who sent each request and compares that login with `ORBIT_OWNER`. Anyone else, or a request it cannot identify, gets no memory. With the `orbit.github-vault` credential installed, memory searches and reads ORBIT's own writable clone of the vault (fetched from GitHub, so it is fresh and shows ORBIT's own writes); without it, it reads the read-only server copy, which lags. Every answer's `source` says which one answered and how fresh it is.

**Vault writes and the config view (general tools, part 1).** Six owner-only chat tools (`vault_policy`, `vault_create_note`, `vault_append_section`, `vault_replace_text`, `vault_set_frontmatter`, `vault_archive_note`) edit the vault under its own `AGENTS.md`: direct writes only where it allows them, a proposal card for anything it protects, secret-shaped text refused, one commit per write (author ORBIT) with a Log line in the same commit, pushed without force and verified on the remote. `orbit_config_view` is a read-only view of how ORBIT is configured. Architecture, policy, authentication, failure behaviour and what must happen before it is switched on: `docs/vault-writes.md`.

**File viewer and editor.** Clicking a file in the left sidebar opens it in the centre pane: its path, then an editor or viewer for its type (Markdown with Edit and Preview tabs, code with syntax highlighting and line numbers, plain text, view-only PDF and image), with Save and Close. Save writes the whole note back through the same vault write pipeline as the chat tools, only while the note still matches what was opened; a masked or cut note opens read-only. The vault snapshot holds Markdown notes only, so the other views are not reachable from the vault yet: `docs/file-viewer.md`.

**Workspace tools (implemented, off, not activated).** Owner-only file tools (`fs_list`, `fs_stat`, `fs_read`, `fs_search`) confined at operation time to operator-configured workspaces, and proposal-only `fs_write`, `fs_patch` and `exec_start` that run only after Rai confirms a digest-bound card; commands run in an unprivileged, network-less bubblewrap sandbox with cgroup limits. Off by default. Activation is an owner-approved path on the existing host: read-only preflight, a host setup confirmed on a card and done by the separately installed root helper `orbit-ops-ws` (`docs/orbit-ops-ws.md`), a bounded validation under the production sandbox, then a separately confirmed enable (and disable at any time): `docs/workspace-tools.md`, section 9.

## Notify and schedule

Owner only. `POST /notifications {text, urgent}` queues a message; `POST /schedule` takes `{text, at}`, `{text, everyMinutes}` (5 or more) or `{text, dailyAt: "HH:MM"}` (Pacific). Jobs are checked every 30 seconds and persist in the service's state directory.

Quiet hours, 23:00-08:00 Pacific, hold non-urgent messages back from Discord; the web page lists them at once (it only shows what someone opens), so a job that finishes at night is on the page then. Every notification records receipts only when delivery is proven: `shown` when the web page listed it in the open notifications panel of a visible tab (a display receipt, not read; `docs/assistant.md`, "Notifications"), `discord` with the message id when Discord accepted it. Discord is off until a webhook URL is installed at `/etc/credstore/orbit.discord-webhook` (root, 0600).

**Watch.** Every 30-second tick, ORBIT checks its own parts. A part `degraded` or `down` for 5 minutes sends one message (urgent only for `down`), and one more when it is `live` again, with how long it was out. A part that goes from degraded to down sends one more, urgent. Parts whose `verifiedAt` is the Unix epoch ("not exercised yet") are ignored.

**Startup smoke checks.** As soon as it is listening, each process runs a bounded check suite once (per-check and 45 s total deadlines, at most 3 at a time, failures isolated, never fatal), so `/status` has evidence from this process without anyone using it. `/status.smoke` and each port's `check` say `pending`, `running`, `passed`, `failed`, `untested`, `skipped` (with why) or `stale`, with the serving commit and pid. Only safe checks run: the policy, a loopback `GET /`, a local vault keyword search, the tick-driven ports, and, when semantic photo search is on and configured, one 19-byte synthetic embeddings request with no retry. Model generation, notifications, job launches and tool calls are skipped, never invoked. `GET /status` only reads. Matrix, bounds and acceptance checklist: `docs/smoke-checks.md`. A job that is `not-started` or `quiet` sends one message with its session link and last check-in; a finished job never does. What was already reported is kept in `watch.json` in the state directory, so a restart does not repeat it, and `/status` shows it as the `watch` part.

## Runs

Owner only. `POST /runs {worker, input, key}` queues background work; `GET /runs/:id` shows its timeline; `POST /runs/:id/cancel` stops it. Workers today: `memory-report {query}` and `model-task {prompt}`.

A run moves through `requested`, `accepted`, `running`, `reviewed` and `delivered`, or ends `failed` or `cancelled`. It is `delivered` only when its notification has a receipt. The same `key` returns the existing run instead of starting another. At most 4 run at once. After a restart, runs that were in flight are re-queued only if their worker is safe to repeat; the rest are marked interrupted. A scheduled job can submit a run with `{text, run: {worker, input}, ...}`.

## Tools

Owner only, read-only. `GET /tools` lists them; `POST /tools/<name>` calls one. Write tools are refused until approvals exist. Today: `github-repo-status {repo: "owner/name"}` returns open PRs and the latest main CI run for a public repo, with no credential. The `tool` worker runs a tool as a background run, so a schedule can deliver it, for example a daily repo digest.

## Nodes

Owner only. `GET /nodes` lists the owner's devices on the tailnet, online or offline with last-seen, read from this host's tailscaled every 30 seconds. Devices of other tailnet users are never listed. The owner's chat gets the same summary, so ORBIT can answer "is my laptop on?". Presence only for now: desktop notifications will need a helper on each laptop.

## Research lane

A second job lane for internet research, separate from the build routine: its own Routine and environment with no repository sources, its own setting and credential (`ORBIT_RESEARCH_ROUTINES`, `orbit.research-routine.<name>`), and an API-only runner tool (`tools/orbit-research`). The owner's model discovers both lanes with `routines_list`, proposes research with `research_launch` (Rai confirms, like every launch and steer), reads the stored, validated, source-linked report with `research_result`, and can save it to the vault with `research_save_to_vault` through the existing policy-checked pipeline at a path ORBIT chooses. A research job never opens a PR, starts a review, writes `orbit-work` or launches a build. **Not provisioned:** the lane reports `unconfigured` until an operator follows `deploy/routines/orbit-research.md` and its smoke test passes. Design, security boundary and what is still unverified: `docs/research-lane.md`. The runner's bootstrap (the routine prompt's step 2) downloads its tool with bounded retries of transport failures only (never a 401/403, a certificate failure or a digest mismatch), installs it only after the digest matches, and may send one authenticated, fixed-field `bootstrap` failure report; ORBIT records when it sent the tool, and a job with no callback reads `not-started` after 10 minutes, which is never treated as proof of failure (`docs/research-lane.md`, "Bootstrap and the callback deadline"). A changed prompt must be pasted into the saved routine by hand.

## Cloud runners: `orbit-job`

`tools/orbit-job` is the job protocol for Claude cloud runners. A job's control files live in the private `DragonflyAI-sh/orbit-work` repo on branch `orbit/<job-id>`: ORBIT writes `.orbit/brief.md` and `.orbit/steer/<n>.md`; the runner writes `started.json`, `checkins.jsonl`, `replies/<n>.md` and `summary.md`. Code always goes to the project repo, never `orbit-work`.

```bash
orbit-job start --job <id>        # check out orbit/<id>, record the start, print the brief path
orbit-job checkin "<status>"      # record progress, then show new steers
orbit-job reply <n> <file>        # answer steer n
orbit-job summary --status done|blocked|failed [--repo <dir>] [--code-branch] <file>
```

Each command reports what really happened (`ok git=pushed <sha> api=sent`, `api=failed`, or `FAILED ...`). With `--api <url> --token <token>`, every step also calls ORBIT back and a check-in fetches steers queued through the API; the tool writes them into `.orbit/steer/` so git stays the complete record. If the API is unreachable, the step still lands in git.

**Summary contract.** `orbit-job summary --status done` requires `## PR title` and `## PR body` when the job pushed a code branch, because ORBIT opens the pull request from them. The check runs before anything is written, committed or sent to the API: a refused summary exits 2 with a list of what to fix and leaves no trace, so the runner corrects the file and runs the same command again. Meaningful means a title line of at least 8 characters with letters or digits that is not a placeholder (`TBD`, `TODO`, `n/a`), and a body of at least 40 non-space characters. Headings are matched the way ORBIT reads them (own line, case-insensitive, `src/pull-requests.ts`). `blocked` and `failed` summaries, and `done` summaries of jobs with no pushed code branch (research, reviews), are unchanged.

*How a pushed code branch is detected.* The evidence is job-specific: the branch `orbit/<job-id>` exists on the `origin` of a project checkout (`git ls-remote`). Checkouts considered are `--repo <dir>` (repeatable), `ORBIT_JOB_REPOS` (colon-separated), the current directory, and every checkout directly under the directories in `ORBIT_JOB_SEARCH` (default `$HOME:/home/user`). The `orbit-work` checkout is skipped, since its `orbit/<job-id>` is the control record. If origin cannot be reached, the checkout's remote-tracking ref `origin/orbit/<job-id>` counts. *Limitations:* a push made without a visible checkout (GitHub API tools, a checkout outside the search directories) is not detected unless the runner passes `--repo` or `--code-branch`; a branch that was never pushed, or a push to a differently named branch, is not evidence; the check is the runner-side gate only, so a summary written by hand into `orbit-work` or sent straight to the API bypasses it, and ORBIT still falls back to `ORBIT job <id>` and the whole summary for the PR text when the sections are absent. The API event carries the whole summary up to 200,000 bytes (`orbit-job` flags `textComplete: false` beyond that, and ORBIT then reads the whole file from git before acting); the listener accepts bodies up to 640 KB. Older tool versions sent only the first 4000 bytes, which is why a long summary lost its `## PR title` and a review lost its verdict line: the tool is copied from the commit ORBIT names, so the fix applies to jobs started after it is deployed.

**Running release in the status line.** Expanding the header's status indicator shows, under the pills, when the running release was deployed and its commit. Both come only from `GET /status`: the commit is `commit` (the `ORBIT_COMMIT` the process runs, from the release's `release.env`), shown as 7 characters with the full commit on hover and for screen readers; the time is `deploy.lastDeployed.at`, which `deploy/pull-deploy.sh` records in `state/deploy.json` once that commit is verified serving, shown in ORBIT's configured zone (`src/time.ts` `ZONE`) with the zone's abbreviation. The time is shown only when that record names the running commit; otherwise, or when either value is missing or malformed, the row says "Unavailable" (the reason is the hover text). Nothing is taken from the page's clock, a commit date, process start or a file time. Tests: `test/deploy-info.test.ts`.

**Tool commit provenance.** The fire text names the commit ORBIT is running; the runner verifies that commit on `main`, copies the tool out of it, and tells the tool what it verified: `orbit-job start --job <id> --tool-commit <40-hex>` (or the environment variable `ORBIT_JOB_TOOL_COMMIT`; the option wins). The tool never infers it from the job checkout, HEAD or ORBIT's version. A missing value is recorded as the literal `unknown`; a value that is not a full lowercase 40-character hex commit makes `start` fail rather than record junk. It is written as `toolCommit` in `.orbit/started.json` and sent as `toolCommit` on the `started` API event (ingestion drops anything malformed, or on other event types). ORBIT stores it on the job (`Job.toolCommit`; the git-record fallback, `gitReconciler`, reads it from `started.json` when the API missed the start). `/jobs` (rows and detail) return `toolCommit` (`unknown` if absent, as for every job started before this field) and `toolCommitStatus`: `match` or `mismatch` against `ORBIT_COMMIT` (the same value `/status` reports, never the job branch), or `unknown` when either side is unknown. Only `mismatch` is flagged in the Jobs view; an unknown commit is shown as "tool commit: unknown", never as a mismatch. Limitation: the commit is the runner's own claim, so ORBIT records what was reported and cannot itself prove the runner verified it.

**Fire text.** Every job's fire text (the owner's launch route, a confirmed chat proposal, and ORBIT's own review launches all build it in `jobLauncher`, `src/job-launch.ts`) ends with `Tool commit: <sha>`: the commit of the ORBIT runtime that generated it, from `ORBIT_COMMIT` (written to `release.env` by `deploy/pull-deploy.sh`, and the same value `/status` reports), not the tip of main and not the job branch. If it is unset, `unknown`, or not a hex commit id, the line says `Tool commit: unknown`; no SHA is ever guessed. The existing lines (`Job id`, `API`, `Token`) are unchanged.

**Job API.** The owner registers a job with `POST /jobs {id}` and gets a token that works for that one job and expires in 24 hours; `POST /jobs/<id>/steer {text}` queues a steer. A launch whose outcome ORBIT's record cannot settle (`dispatch-unknown`, or accepted with no runner event) can be reconciled by the owner with `POST /jobs/<id>/reconcile`: a preview, then a digest-bound confirmation, appended to an audit log beside the job store. Provider evidence is the owner's report, abandoning tracking is never a cancellation, and late runner events outrank it (`docs/reviews/launch-reconciliation.md`, section 9). Runners talk to a separate listener (`ORBIT_INGRESS_PORT`, bound to 127.0.0.1). It is published by a second Tailscale node, `orbit-jobs`, with its own identity, on port 443, because the cloud sandbox proxy only reaches 443. `deploy/install.sh` sets that node up when the one-time auth key `/etc/credstore/orbit.tailscale-jobs` exists that serves only `POST /v1/jobs/<id>/events` and `GET /v1/jobs/<id>/steers`, with the job's token. It has no access to memory, tools or owner routes. Replies and summaries notify the owner. `tools/orbit-job/install.sh` installs the tool and its skill (`SKILL.md`) in a cloud session.

## Model

Set `ORBIT_MODEL` in `/opt/orbit/orbit.env`. ORBIT then uses "Sign in with ChatGPT" token sharing, the method OpenClaw's OpenAI plugin uses: ChatGPT authorizes eligible Responses API calls (`api.openai.com/v1/responses`) on your subscription.

To sign in, press "Sign in with ChatGPT" on the web page, open the link and approve ORBIT. The browser then lands on a `localhost:8080` address that will not load, because ORBIT runs on the server; paste that address into the page. ORBIT verifies the identity token against OpenAI's published keys, checks that token sharing was granted, and keeps its own login in its private state directory. It renews the login itself and never shares OpenClaw's, because every renewal replaces the token.

**Renewal.** The 30-second tick renews the ChatGPT login in the background when the access token has 10 minutes or less left (or half its last lifetime, if shorter, so a short-lived token is not renewed in a loop), with no model call. A call that finds the token within 5 minutes of expiry still renews it on demand. The background renewal and calls share one request, and the new token is saved before it is used. A failed renewal is retried after 1, 2, 4, 8, then 15 minutes; a revoked login is not retried. Status stays `live` through routine renewals. A failed renewal is `degraded` while the old token still works and `down` once it has expired, with `verifiedAt` the time of the failure; the watch alerts only if that lasts 5 minutes. Renewal never sets the model's last-answer time and never clears a failed model call. On SIGTERM/SIGINT ORBIT waits (up to 10 s) for a renewal in flight so a rotated token is saved.

**Idle is not degraded.** The model port is exempt from the 5-minute "not verified" rule that other ports keep. Each 30-second tick re-checks the saved login on disk (complete, token sharing granted, unexpired, no failed renewal); a pass, like a successful renewal, advances `verifiedAt`, so an idle healthy model stays `live`. These checks are not model answers: they never set the last-answer time and never clear a failed model call. Degraded/down come only from errors: a failed call is `down` until a later call succeeds (neither elapsed time, a login check nor a renewal recovers it); a failed renewal is `degraded` while the old token works and `down` once it expires, recovering when a renewal succeeds; an incomplete or revoked login, or an expired token not yet renewed, is reported as such. A model never exercised since startup keeps its existing semantics (local readiness, or the epoch `verifiedAt` the watch ignores). If the tick itself stopped, the token would eventually expire and the model would report that.

**OpenRouter fallback.** Off by default: while ChatGPT is usage- or rate-limited, a paid OpenRouter model can answer with the same tools and confirmations as ChatGPT (no photos) and a durable spend guard. Same tools means the actions that need no card on ChatGPT need none on the fallback either (section 3 vault writes, `notify`, `ops_sys_cancel_reboot`); the model port is red when neither model can reply, amber only after a fallback call has succeeded. See `docs/openrouter-fallback.md` (design, limits of the cap, activation and rollback).

An OpenAI API key at `/etc/credstore/orbit.openai` (root, 0600) takes precedence if present. Without either, replies are mock and `/status` says why.

**Server operations (tier 2).** ORBIT can propose a restart, a deploy now, a rollback, a change to five `orbit.env` settings, or a vault refresh. Each is an owner-only proposal that does nothing until Rai confirms the exact action, and then runs through a separate privileged helper whose result ORBIT reports only once it has verified `/status`. See `docs/orbit-ops-admin.md` (privileges, install commands, acceptance checks).

**Server operations (tier 3).** Code only; not installed or verified on any host. ORBIT can propose installing OS updates, rebooting, or enabling/disabling the existing orbit-jobs Tailscale Funnel. Each is a separate owner-only proposal with a separate confirmation, bound to an exact digest, and runs through a separate privileged helper (`deploy/install-sys.sh`, which nothing runs automatically and which needs `--approved-by-owner`). Updates never reboot; a reboot or Funnel change counts as done only when the helper observed it. See `docs/orbit-ops-sys.md` (threat model, update policy, Funnel topology, rollback, staged live acceptance, evidence gaps).

**Rollback drill.** `deploy/pull-deploy.sh --drill` is an opt-in, operator-run drill of the real rollback path; see `docs/rollback-drill.md`. An app deploy does not update `/usr/local/lib/orbit/pull-deploy.sh`; the runbook says how to verify and install it.
